# Exhaustive sweeps and property-based tests

Two more ways the host tests check the real firmware files (`Core/Src/pedal_checks.c`, `torque_map.c`, `power_limit.c`, `torque_diag.c`), next to the unit tests. Neither needs bench data.

| | Exhaustive (`tests/test_exhaustive.c`) | Property-based (`tests/pbt/`) |
|---|---|---|
| Inputs | Every value where the space is small, fixed grids where it isn't | Generated by Hypothesis, biased toward boundaries |
| Finds | Any bad input in the swept space, every run | Bad input *sequences* (timing, history) a grid can't enumerate |
| A failure shows | The exact input | The **smallest** failing input (Hypothesis shrinks it) |
| Run | `make -C tests` (~2 s per build) | `make -C tests pbt` (~15 s; `PBT_EXAMPLES=5000` for ~4 min) |
| Needs | A C compiler | Python 3; Hypothesis is installed into `tests/build/venv` |

Both run in CI. Both are built with regen off, regen on, and `MIN_APPS`.

## Exhaustive

| Test | Space | Checks |
|---|---|---|
| `test_every_apps_pair` | All 4096 × 4096 APPS1/APPS2 counts | Invalid flag exactly outside the range, cut that tick (T.4.2.10); valid pairs never cut on the first tick, implausible exactly when > 10% apart (T.4.2.4) |
| `test_apps_percent_monotonic_in_each_sensor` | Same | Pressing either sensor never lowers the APPS travel used for torque |
| `test_every_bse_count` | All 4096 BSE counts | Cut exactly when out of range or braking with 30% throttle (EV.4.7); RTD brake check exactly for pressed, valid counts |
| `test_map_grid` | Pedal (10 001) × speed (2001) × 4 brake values | Torque bounds, no regen under 5 km/h, with the brake on, backward, or with regen off (EV.3.3.3); torque never falls as the pedal goes down |
| `test_request_step_from_any_state` | One filter step from ~45 M (state, input, cap) points | Output between 0 and the capped target (EV.3.1.3, EV.3.3.1), slew and regen ramp limits, cut = 0 Nm, from any state, reachable or not |
| `test_every_rpm_speed` | Every int16 rpm × every age to stale | Speed sign, monotonic, trusted speed never above the reported one, 0 once stale |
| `test_every_rpm_power_cap` | Every int16 rpm | Cap in (0, `MAX_TORQUE`], DC power ≤ 75 kW |
| `test_apps_disagreement_timing`, `test_range_latch_timing` | Every sequence of up to 3 (fault, good) runs, lengths around each boundary (113 k sequences each) | Matches a small model of the documented timers tick for tick (T.4.2.5, T.4.3.3) |

## Property-based

Each property is a rule that must hold for every input Hypothesis can think of. Most generate whole drives (lists of "this reading for N ticks" segments, starting at any `HAL_GetTick()` value, so timers cross the uint32 wrap).

| Property | Rule |
|---|---|
| `test_pedal_chain_meets_rule_obligations` | Any sensor readings: cut when out of range, latched after 100 ms out, cut after 100 ms of disagreement, EV.4.7 armed at drive entry and held until APPS ≤ 5% |
| `test_healthy_pedals_only_cut_for_ev47` | Healthy, agreeing sensors (with noise): torque is cut only for EV.4.7, and comes back at 5% |
| `test_request_obeys_rules_every_tick` | Any pedal/brake/speed/cut/power-cap history: cut = 0 Nm, never above the request or the cap, regen only ≥ 5 km/h with the brake off, slew and regen ramp limits |
| `test_held_pedal_gets_its_torque` | Holding the pedal reaches the requested (or capped) torque in 0.5 s |
| `test_trusted_speed_only_lowers` | Trusted speed ≤ reported, never flips sign, 0 when stale, any tick values |
| `test_power_cap_holds_any_speed`, `test_power_cap_assumes_max_speed_when_stale` | EV.3.3.1 cap at any speed; stale speed assumes 6000 rpm |
| `test_deci_nm_saturates_and_truncates` | Any float32 (NaN, ±inf too) → 0x0C0/0x502 counts saturate and never flip sign |
| `test_rtd_brake_only_for_pressed_valid_bse` | EV.10.6.2 |

The checks are **rule obligations** (what the rulebook demands), not a copy of the firmware's logic, so a stricter firmware passes them. Being too strict is checked separately (`test_healthy_pedals_only_cut_for_ev47`, `test_held_pedal_gets_its_torque`).

### Reading a failure

Hypothesis prints the shrunk input, for example (a latch broken on purpose):

```
AssertionError: tick 102: should be latched
Failing test case: test_pedal_chain_meets_rule_obligations(
    segments=[(0, 0, 375, 102)],    # APPS1, APPS2, BSE counts, ticks
    start=0,
)
You can reproduce this test case by temporarily adding @reproduce_failure(...)
```

So: both APPS at 0 counts (shorted to ground) for 102 ticks should have latched. Failures are also saved in `tests/build/hypothesis-db` and tried first on the next run.

## How well do they catch bugs?

Checked 2026-10-23 by breaking a copy of the firmware on purpose (mutation testing):

- Exhaustive: 13 of 14 caught. The survivor (5 km/h regen cutoff moved to 4.9) changes nothing, because the speed fade already gives 0 Nm below 8 km/h.
- Property-based: 6 of 9 caught. Survivors: the startup no-grace APPS cut (stricter than the rule, covered by `test_reset_disagreement_cuts_*`), the NaN line in `torqueDiag_deciNm` (NaN converts to 0 anyway on these CPUs), and a 10% looser slew limit (the low-pass filter never reaches it from a reachable state; the exhaustive sweep catches it because it starts from any state).

## What these can't check

Only the HAL-free files. CAN, interrupts, timers and the RTD sequence (`main.c`, `fdcan.c`, `vcu_state.c`) need the bench: [bench-plan.md](bench-plan.md).
